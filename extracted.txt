Autenticación — Supabase Auth + JWT Validation 3.1 Flujo de Autenticación Completo El flujo de autenticación sigue este camino: Usuario hace login en frontend via Supabase SDK (email/password u OAuth) Supabase devuelve access_token (JWT RS256, exp: 1h) + refresh_token Frontend almacena tokens; incluye Authorization: Bearer {access_token} en cada request FastAPI middleware extrae y valida JWT localmente usando JWKS de Supabase JWT válido → se extrae user_id (sub) + metadatos (role, plan) Se crea/sincroniza usuario en base de datos local si es primera vez Request continúa con usuario autenticado en contexto 3.2 Implementación JWT Validation en FastAPI # app/core/security.py import httpx from jose import jwt, JWTError, ExpiredSignatureError from fastapi import HTTPException, status, Depends from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials from app.core.config import settings bearer_scheme = HTTPBearer() class SupabaseJWTValidator:     def __init__(self):         self._jwks = None         self._jwks_fetched_at = None     async def _get_jwks(self) -> dict:         # Cache JWKS por 1 hora — no llamar a Supabase en cada request         now = datetime.utcnow()         if self._jwks is None or (now - self._jwks_fetched_at).seconds > 3600:             async with httpx.AsyncClient() as client:                 resp = await client.get(settings.SUPABASE_JWKS_URL)                 self._jwks = resp.json()                 self._jwks_fetched_at = now         return self._jwks     async def validate(self, token: str) -> dict:         try:             jwks = await self._get_jwks()             payload = jwt.decode(                 token,                 jwks,                 algorithms=['RS256'],                 audience='authenticated',                 options={'verify_exp': True}             )             return payload         except ExpiredSignatureError:             raise HTTPException(401, 'Token expired')         except JWTError as e:             raise HTTPException(401, f'Invalid token: {e}') jwt_validator = SupabaseJWTValidator() # app/api/deps.py — Dependency Injection async def get_current_user(     credentials: HTTPAuthorizationCredentials = Depends(bearer_scheme),     db: AsyncSession = Depends(get_db), ) -> User:     payload = await jwt_validator.validate(credentials.credentials)     supabase_id = payload['sub']     user = await user_repo.get_by_supabase_id(db, supabase_id)     if not user:         # Sincronización automática en primer login         user = await user_service.sync_from_supabase(db, payload)     return user # Dependency para roles def require_role(*roles: str):     async def check(user: User = Depends(get_current_user)):         if user.role not in roles:             raise HTTPException(403, 'Insufficient permissions')         return user     return check 3.3 Roles y Permisos (RBAC) Role Permisos Límites Uso free Upload, generate básico 10 docs, 100 generaciones/mes Usuario gratuito pro Todo + batch, history Ilimitado documentos Suscripción mensual admin Todo + panel admin Sin límites Equipo interno Los roles se almacenan en el campo app_metadata.role del JWT de Supabase y se sincronizan a la tabla local users. app/modules/ai/embeddings.py from openai import AsyncOpenAI from app.shared.cache import redis_cache import hashlib class EmbeddingService:     MODEL = 'text-embedding-3-small'  # 1536 dims, $0.02/1M tokens     BATCH_SIZE = 100                   # OpenAI permite hasta 2048/request     def __init__(self, client: AsyncOpenAI):         self.client = client     async def embed_chunks(self, chunks: list[str]) -> list[list[float]]:         # Agrupar en batches para eficiencia         all_embeddings = []         for i in range(0, len(chunks), self.BATCH_SIZE):             batch = chunks[i:i + self.BATCH_SIZE]             # Verificar cache antes de llamar a OpenAI             cached, uncached_idxs, uncached_texts = [], [], []             for j, text in enumerate(batch):                 cache_key = f'emb:{hashlib.md5(text.encode()).hexdigest()}'                 cached_val = await redis_cache.get(cache_key)                 if cached_val:                     cached.insert(j, cached_val)                 else:                     uncached_idxs.append(j)                     uncached_texts.append(text)             if uncached_texts:                 response = await self.client.embeddings.create(                     model=self.MODEL,                     input=uncached_texts,                 )                 for k, emb in enumerate(response.data):                     text = uncached_texts[k]                     cache_key = f'emb:{hashlib.md5(text.encode()).hexdigest()}'                     # Cache por 30 días — embeddings son deterministas                     await redis_cache.set(cache_key, emb.embedding, ttl=2592000)                     cached.insert(uncached_idxs[k], emb.embedding)             all_embeddings.extend(cached)         return all_embeddings   💰 AHORRO DE COSTOS     El caché de embeddings es crítico. El mismo texto siempre produce el mismo embedding con el mismo modelo. Caché = 0 costo en re-procesamiento. En producción puede ahorrar 60-80% del costo de embeddings. 6. RAG Pipeline — Retrieval Augmented Generation 6.1 Arquitectura RAG Completa El pipeline RAG de Exam Prep AI sigue una arquitectura de dos fases: Offline (indexación) y Online (consulta). Fase Offline — Indexación PDF upload → texto extraído → chunks creados → embeddings generados → almacenados en pgvector Fase Online — Consulta Usuario envía pregunta/chat Pregunta se convierte a embedding con el mismo modelo Búsqueda de similitud coseno en pgvector sobre los documentos del usuario Top-K chunks recuperados (por defecto K=5-8) Chunks + pregunta + historial de conversación → enviados a LLM LLM genera respuesta fundamentada en el contexto Respuesta devuelta al usuario con referencias a fuentes 6.2 Implementación de Retrieval # app/modules/ai/retrieval.py from sqlalchemy import select, func from pgvector.sqlalchemy import Vector class RetrievalService:     async def similarity_search(         self,         db: AsyncSession,         query_embedding: list[float],         document_ids: list[UUID],         top_k: int = 6,         similarity_threshold: float = 0.75,     ) -> list[DocumentChunk]:         # Búsqueda coseno con pgvector — operador <=>         result = await db.execute(             select(                 DocumentChunk,                 (1 - Embedding.vector.cosine_distance(query_embedding)).label('similarity')             )             .join(Embedding, DocumentChunk.id == Embedding.chunk_id)             .where(DocumentChunk.document_id.in_(document_ids))             .where((1 - Embedding.vector.cosine_distance(query_embedding)) >= similarity_threshold)             .order_by(Embedding.vector.cosine_distance(query_embedding))             .limit(top_k)         )         return result.all() # Índice HNSW en pgvector (CRITICAL para performance) -- migrations: crear índice para vectores CREATE INDEX ON embeddings USING hnsw (vector vector_cosine_ops) WITH (m = 16, ef_construction = 64);   ⚡ PERFORMANCE CRÍTICO     Sin el índice HNSW, una búsqueda en 1M vectores tarda 8+ segundos (full scan). Con HNSW: < 50ms. Crear este índice desde la primera migración. 6.3 RAG Pipeline con Memoria Conversacional # app/modules/ai/pipelines/rag.py class RAGPipeline:     async def run(         self,         question: str,         document_ids: list[UUID],         conversation_history: list[Message],         user: User,     ) -> RAGResponse:         # 1. Generar embedding de la pregunta         query_embedding = await self.embedding_svc.embed_single(question)         # 2. Recuperar chunks relevantes         relevant_chunks = await self.retrieval_svc.similarity_search(             self.db, query_embedding, document_ids, top_k=6         )         # 3. Construir contexto con MMR (Maximal Marginal Relevance)         context = self._build_context(relevant_chunks, max_tokens=3000)         # 4. Construir mensajes con memoria conversacional         messages = self._build_messages(question, context, conversation_history)         # 5. Llamar a LLM         response = await self.llm.chat(             messages=messages,             model='gpt-4o',             temperature=0.1,  # Baja temperatura para respuestas factuales             max_tokens=2000,         )         # 6. Log de tokens para billing         await self.usage_svc.log(user.id, 'rag_chat', response.usage)         return RAGResponse(             answer=response.content,             sources=[c.to_source_ref() for c in relevant_chunks],             tokens_used=response.usage.total_tokens,         ) 6.4 Memoria Conversacional Para chats contextuales, usar una estrategia de ventana deslizante con resumen: Mantener las últimas N=10 interacciones en memoria activa Si el historial supera el límite de tokens, comprimir las interacciones más antiguas con un resumen Guardar resumen + últimas N en BD para persistencia entre sesiones Los embeddings del historial pueden usarse como contexto adicional en el retrieval 7. Roadmap Backend y Errores Comunes a Evitar 15.1 Roadmap de Desarrollo — Fases Fase 1 — Fundación (Semanas 1-3) Setup del proyecto: estructura de carpetas, Docker Compose, PostgreSQL, Redis Modelos de base de datos y primeras migraciones Alembic Supabase Auth integrado: JWT validation, sync de usuarios Upload de documentos: endpoint + Supabase Storage Procesamiento básico de PDF con pdfplumber Chunking y embeddings con OpenAI Tests unitarios básicos y CI/CD pipeline Fase 2 — IA Core (Semanas 4-6) Celery workers: process_document, generate_embeddings pgvector: índice HNSW, búsqueda de similitud RAG pipeline completo con memoria conversacional Generación de quiz y flashcards Rate limiting por usuario y plan Tracking de uso de tokens y costos Integration tests para flujos IA Fase 3 — Producto (Semanas 7-9) Planes de estudio IA personalizados Resúmenes estructurados con secciones WebSockets para progreso en tiempo real de jobs Historial completo de generaciones Sistema de créditos / suscripciones Panel de administración básico Observabilidad: Sentry, Prometheus, Grafana Fase 4 — Scale (Semanas 10-12) OCR para PDFs escaneados (Tesseract / AWS Textract) Multi-document RAG: queries sobre múltiples documentos Batch generation: procesar múltiples generaciones en paralelo Cache avanzado: semantic caching de queries similares Performance tuning: profiling, índices, query optimization Load testing y chaos engineering básico 15.2 Errores Comunes a Evitar — Basados en Experiencia Real   ❌ ERROR #1     Hacer llamadas a OpenAI síncronas en el request handler. Siempre usar async/await o delegar a Celery para generaciones > 2s.   ❌ ERROR #2     No versionar la API desde el día 1. Cuando tengas clientes móviles con versiones antiguas instaladas, no puedes romper /api/documents sin /api/v1 y /api/v2.   ❌ ERROR #3     Guardar el Supabase service key en el frontend o en logs. Este key tiene acceso total a tu base de datos. Solo en variables de entorno del backend.   ❌ ERROR #4     No cachear embeddings. El mismo texto siempre produce el mismo embedding. Sin caché, re-procesar un documento cuesta el doble.   ❌ ERROR #5     Chunks demasiado largos o cortos. < 200 tokens pierden contexto, > 1200 tokens diluyen el retrieval. Testear con tu contenido real.   ❌ ERROR #6     No crear el índice HNSW en pgvector antes de escalar. Con >100K vectores sin índice, las queries tardan segundos.   ❌ ERROR #7     Worker prefetch_multiplier > 1 sin saberlo. El default de Celery es 4, lo que significa que un worker acapara 4 tareas. Para tareas largas de IA, usar 1.   ❌ ERROR #8     No trackear tokens y costos desde el inicio. En producción con 1000 usuarios, el costo de OpenAI puede dispararse en horas sin alertas.   ❌ ERROR #9     Migrations con DROP TABLE o cambios destructivos en producción. Usar migraciones aditivas: agregar columnas, no modificar tipos en producción.   ❌ ERROR #10     No implementar soft delete. En una plataforma con historial, los usuarios esperan poder recuperar documentos eliminados. Agregar después es costoso. 15.3 Lo que Haría Como Arquitecto Senior Día 1:  Crear la estructura completa de carpetas aunque estén vacías. Definir interfaces (ABCs) de los servicios clave antes de implementarlos. Esto fuerza a pensar en contratos, no en implementaciones. Semana 1:  Implementar el flujo de autenticación completo end-to-end antes de cualquier feature. Es el fundamento de todo. Siempre:  Medir antes de optimizar. No pre-optimizar el RAG pipeline sin datos reales de qué queries fallan y por qué. Para vectores:  Empezar con pgvector. Si el día de mañana necesitas migrar a Qdrant, la interfaz abstracta del repositorio hace que sea un cambio de 2-4 horas, no semanas. Para costos:  Implementar gpt-4o-mini para el 80% de las generaciones. Reservar gpt-4o para cuando el usuario explícitamente lo solicite o para análisis complejos. Impacto: 75% de reducción en costos de inferencia. Para deuda técnica:  Dedicar el 20% de cada sprint a refactoring y tests. Un módulo sin tests es deuda técnica garantizada.
